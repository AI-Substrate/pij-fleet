# pij-rs and Microsoft Defender on macOS

On a Mac with Microsoft Defender for Endpoint, the `pij-rs daemon` can be the largest source of real-time scans. Defender checks every program launch, and the daemon launches many short-lived child processes (tmux and process probes). The scans add CPU load and can show up as system-wide input stutter.

## Measure it

```sh
mdatp diagnostic real-time-protection-statistics --output json \
  | jq -r '.counters | sort_by(-(.totalFilesScanned|tonumber)) | .[:10][] | "\(.totalFilesScanned)\t\(.id)"'
```

Run it twice a minute apart and compare the counts. On 2026-10-19 one dev Mac measured about 13,700 scans from pij-rs in a few minutes (about 75 a second, roughly five times every other process combined). With the exclusions below in place, it measured 5 in the next 60 seconds. Those numbers are a snapshot; re-measure on your own machine.

## Exclude the daemon

Exclusions usually need admin rights, or your IT department if the device is managed:

```sh
mdatp exclusion folder add --path "$HOME/.pij-rs"
mdatp exclusion process add --path "$HOME/.local/share/pij/bin/pij-rs"
mdatp exclusion list    # verify
```

- **The binary path:** the process exclusion matches one binary path. `just rs-install` installs pij-rs as a copy at `~/.local/share/pij/bin/pij-rs` and links `$(npm prefix -g)/bin/pij-rs` to it (`readlink -f "$(command -v pij-rs)"`), and the daemon runs that copy. Before F187 the link went into `target/release/pij-rs` in the main checkout, so an exclusion added then names a path the daemon no longer runs from: add the copy's path. If the scan counts climb again, check that the resolved path is the one excluded.
- **The state directory:** the folder exclusion assumes the default `~/.pij-rs`. If you run the daemon with another `--state-dir`, exclude that directory instead.

## What pij does about launches (plans 180 and 182)

Exclusions don't stop Defender's EDR inspecting each process launch, so pij now launches far fewer:

- **Daemon tmux reads.** The pane observer used to start three `tmux` clients per tracked pane every 600 ms. The daemon now keeps one tmux control-mode client (`tmux -C`) and sends its reads (`list-panes`, `capture-pane`, `display-message -p`, `show-options`) over it. Writes still start a tmux client. If the control client is unavailable, slow or lost, the read starts a client as before and the control client is replaced, so answers never change. `tmux list-clients` shows the control client.
  - **What stops it writing.** Only pij's own code: an allow-list of those four reads (every other command starts a client instead) and single-quoting of every argument (an argument that can't be quoted also starts a client). The `read-only` attach flag only refuses keyboard input; commands sent over the control pipe run with full rights.
  - **Its own session, `_pij`.** The client attaches to a detached session named `_pij` (one window running `sleep`), which it creates if absent. While `_pij` holds only that window, it is destroyed when no pij client is attached. The client never starts a tmux server, and it leaves when `_pij` is the only session, so the server still exits when you close your last session. pij never lists the control pane itself. Expect one `_pij` row in session pickers and `tmux ls`. A bare `tmux attach` behaves as without pij. `pij spawn --session _pij` is refused (`E-RS-CONTROL-SESSION`).
  - **One attach at a time (F229).** Two control clients attaching to one server at the same moment, each switching `_pij`'s `destroy-unattached` on, crash tmux 3.6a (a SIGSEGV that takes every session with it). So a client holds an exclusive `flock` from its attach until its setup has answered. The lock is the server's (F238): `.<server>.pij-control-attach.lock` beside the server's socket, in tmux's own `tmux-<uid>` directory, so every pij process using that server shares it whatever its state directory. pij never creates that directory: without it there is no server to attach. It takes the lock there only while that directory is as private as tmux requires (a real directory, yours or root's and sticky, writable by others only if sticky); beside a socket in any other directory it takes it in its state directory instead. The file is opened without following a symlink, and refused unless it is a regular file of yours with one link, before anything about it is changed (S292-001). While another pij process holds that lock, this one neither waits (its reads run on the daemon's async workers) nor starts a tmux client per read (that fallback would cost about 5 launches a second per pane): each read is skipped and reported unknown, launching nothing, and tries the lock again. The holder lets go within its own 3 s handshake limit; only if it holds the lock for 5 s (a frozen process) is the start refused, after which reads start clients as after any failed start. The kernel drops a dead holder's lock, so a crash never blocks the next attach. Cost: one lock per client start (daemon start, or a replacement after a lost client), nothing per read.
  - **A clean exit (F238).** A control client that is dead but not yet lost does not count as attached, so `destroy-unattached` could destroy `_pij` under it, and its own detach notice then read the destroyed session: a tmux SIGSEGV (3.4 and 3.6a). So every client leaves through a teardown it runs over its own pipe while still attached. If it is `_pij`'s only client and `_pij` holds only the control client's own idle pane (told by its start command, never by a count), it kills `_pij`; otherwise it switches `_pij`'s `destroy-unattached` off and leaves `_pij` to its other clients, so a pane of yours that is all `_pij` holds is never killed. Only then is it stopped. The whole exit is bounded: the teardown is written and answered on its own thread and waited on for at most 1 s, so a dead pipe, a full one or a frozen server never holds it, and the stopped client is reaped within 1 s more or handed to a thread that reaps it. Every way a client leaves takes this path: the daemon stopping (SIGINT or SIGTERM, which both stop it gracefully), a replacement after a slow or lost reply, `_pij` left alone, the adapter dropped. `destroy-unattached` stays on while attached and `_pij` holds only the idle pane, so a client that dies uncleanly (SIGKILL, a crash, out of memory) still has `_pij` cleaned up, with the old crash risk for that exit only. Cost: one command over the existing pipe and one short-lived thread per client exit, no process.
  - **A stop that finishes (F242).** A stopping daemon releases its control client first, alongside the stop of every worker, so the teardown never waits behind anything else; a tmux read after that (a worker's last tick, a request still in flight) starts one client, as any read without a control client does. It then gives HTTP requests in flight 5 s to finish and drops every connection still open after that: an event stream (`pij tail`, the extensions') never ends on its own, and before F242 one open stream kept the daemon from ever exiting, so every bounce ended in a SIGKILL and the teardown never ran. `just bounce-rs` also switches `_pij`'s `destroy-unattached` off on the daemon's server just before it signals the old daemon (one tmux call per bounce, given at most 2 s and then killed, so a frozen server never holds the bounce; no server or no `_pij` is fine), so even a SIGKILL can't destroy `_pij` under the dying client; the new daemon's setup switches it back on. It then waits 30 s on the clock before a SIGKILL, then up to 5 s more, and starts no new daemon while the old one or its port remains.
  - **Known effect: untargeted commands from outside tmux.** A tmux command run from outside tmux with no `-t` (for example `tmux new-window` from a script) goes to the most recently active session. Attaching a client counts as activity, so after the control client starts or reconnects, such a command lands in `_pij`. That lasts until a keypress in another session makes it more recent, and with no human attached it can last indefinitely. A window or pane that lands in `_pij` stays: pij lists it like any other, and `_pij` is then kept even after the control client leaves. Pass `-t` to target a session. pij's own writes always target.
- **The Copilot status line.** The managed `~/.pij-rs/copilot-statusline-pij.sh` used to start about 20 processes per refresh (jq, awk, git, a `pij-rs whoami` CLI). It now runs `exec pij-rs statusline copilot`, which is one process with the same output bytes. It asks the daemon for `whoami` on every render, so a seat that dies stops showing on the next refresh. Checking that the seat is this session's own (F198) reads the parent pid and start in-process and launches nothing. It reads the git branch from `.git/HEAD` and runs `git` only for a detached HEAD or an ambiguous name.
- **Process probes by absolute path.** On macOS, launching a program by bare name (`ps`) makes `posix_spawnp` try every PATH entry, and each miss creates and tears down a kernel process: with a 32-entry PATH, one `ps` cost 18 process creations. The daemon now runs `/bin/ps` and `/bin/date`, which cost one each. A test (`no_daemon_launch_searches_path_for_ps_or_date`) refuses a bare `ps` or `date` in the daemon crates.
- **`git` and `tmux`, resolved once (plan 182).** These live wherever you installed them, so a fixed path would be wrong. The daemon searches PATH for each the first time it launches it, the same way `posix_spawnp` does (the first match that `access(X_OK)` allows wins), and then launches the absolute path it found (`pij_core::program::launch`). It keeps only a found path, so a tool installed after the daemon started is found on its next launch. If a kept path has vanished (an upgrade moved it), it searches again, before the launch or when the launch itself fails with `ENOENT`. A test (`no_daemon_launch_searches_path_for_git_or_tmux`) refuses a bare `git` or `tmux` launch in the daemon crates.
- **Liveness without `ps` (plan 182).** Every liveness check (the 5 s death sweep over every live seat, `whoami`, delivery) used to run `/bin/ps -o lstart= -p PID`. On the live fleet that was `ps.proc-liveness` at 13.1 launches/s with 63 seats, nearly all of the daemon's launches. The daemon now reads the start time in-process: `proc_pidinfo` on macOS, `/proc/<pid>/stat` with `btime` on Linux. It converts that time with libc `localtime_r`, the same conversion `ps` applies, using the offset in force when the process started. A live seat therefore costs nothing. A pid with no process is answered in-process too (`kill(pid, 0)` returns `ESRCH`, the fact `ps` reports as an empty selection), so a dead seat the reaper keeps because its pane is still open costs nothing either. Only a process that exists but can't be read in-process (a zombie, another user's process) runs `/bin/ps` exactly as before, so every answer is unchanged. `ping` counts those launches as `ps.proc-liveness-fallback`; in steady state expect 0, and a non-zero rate names a seat stuck as a zombie or on a recycled foreign pid. The choice of dependency is recorded in [ADR 0001](../adr/0001-in-process-process-start-time.md).
- **UTC offset and registration ancestry (plan 207).** Reading the local UTC offset used to run `/bin/date +%z`, and the Claude binder does that for every pending Claude seat every 5 s, as do FYI claims and reads, adopt, revive and the double-seat check. The offset is now read in-process with libc `localtime_r`, the same call as ADR 0001, so `date.utc-offset` is gone (#127). Registration's ancestry walk used to run one `/bin/ps` per ancestor. It now reads each ancestor's parent and kernel name in-process (`proc_pidinfo` short BSD info on macOS, `/proc` on Linux as before). Only an ancestor whose name is a harness host's (copilot, claude, codex or node) has its argv read, by one single-pid `/bin/ps -p <pid>`, cached for the registration, so `ps.registration-native-process` is at most one per host-named ancestor (#128). Never batch it: on macOS `ps -p a,b` costs about 0.6 s of kernel CPU, while one pid costs nothing. Reading argv in-process on macOS would need `unsafe` (`sysctl(KERN_PROCARGS2)`), which the workspace forbids (ruling C27).

## Measure launches

```sh
just spawn-rate --seconds 20          # total new processes/s, and the pij daemon's share
top -l 2 -o cpu -n 12 -stats pid,command,cpu   # Defender: epsext, wdavdaemon_enterprise, wdavdaemon
```

`spawn-rate` counts every launch from the PID counter and attributes them by parent. Short-lived processes exit before a poll sees them, so the per-parent numbers are lower bounds. Compare before and after a change on the same fleet.

To see which daemon code launches what, read the daemon's own counter:

```sh
pij-rs --json ping | jq '{pid: .data.pid, spawns: .data.spawns}'   # {pid, spawns: {total, by_op: {"ps.proc-liveness-fallback": N, ...}}}
```

The counts are exact and run since the daemon started, so take two readings a known number of seconds apart and divide the difference. The counter resets when the daemon restarts, so record `data.pid` with each reading: a before and after pair compares only when both show the same pid. Each operation is named `<program>.<site>`, so `ps.*` names which code runs `ps`. A test (`crates/testkit/tests/spawn_sites.rs`) fails when a daemon launch site doesn't record itself.

## What exclusions don't fix

- **EDR monitoring:** the exclusions stop antivirus file scanning only. Defender's EDR component (`wdavdaemon_enterprise`) still observes every process launch, so the daemon's process launches still cost EDR CPU. Only the device's administrators can tune that.
- **The daemon's own CPU use:** pij-rs's CPU use without scanning is a separate issue, tracked in [pij-fleet#62](https://github.com/AI-Substrate/pij-fleet/issues/62).
- **`open()` is not free either:** Defender inspects file opens as well as launches. Plan 185 measured single opens of a daemon state file at 3–138 ms. So a loop that opens files every tick costs CPU here even when it launches nothing. [daemon-cost.md](daemon-cost.md) lists what the daemon still opens, and how to measure it.

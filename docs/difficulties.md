# Difficulty ledger

Every difficulty encountered while working on pij gets a row here, with a
severity. Every workaround becomes either an immediate fix (encode it) or a
wishlist entry tagged `stretch:`. See "Self-improvement loop" in `AGENTS.md`.

| ID | Date | Severity | Difficulty | Resolution / encoding |
|----|------|----------|------------|-----------------------|
| D-167-1 | 2026-10-08 | high | A peer told to work in a stream worktree issued relative-path edits; the agent tool resolved them against its own cwd (the main checkout), silently editing `main`. Caught by an empty `git status` in the worktree. | Reverse-applied the exact patch in main and re-applied it in the worktree. `stretch:` pij peer spawn for a worktree task should start the seat with cwd = the worktree, so relative paths cannot reach main. Until then: absolute worktree paths for every edit. |
| D-167-2 | 2026-10-08 | low | `harness checks` failed `test` because the shell sets both `NO_COLOR` and `FORCE_COLOR`; node prints a warning on stderr that `skills/flow-pair/test/cli-learning.test.ts` asserts is empty. | Run the gate under `env -u FORCE_COLOR`. `stretch:` have that test (or the gate) clear the conflicting colour env for its subprocess. |
| D-167-3 | 2026-10-08 | medium | To honour the C12 load limit an agent stopped its own `harness checks` with `pkill -f 'harness checks'`; command-line patterns match every seat's run on the machine, so a peer's gate may have been killed. | Stop only what you started: hold the PID (`$!`/background job id) and kill that process group. `stretch:` a C12 wrapper that checks load before starting and owns its process group, so stopping is never a pattern match. |
| D-pa-1 | 2026-10-09 | low | A daemon test fixture named its temp git repo `pid-<clock nanos>`. The macOS clock only changes every microsecond, so two tests starting together got the same directory and one `git init` failed with "File exists": the suite failed in 2 of 3 runs. | A per-process atomic counter names the directory (`pa_watchdog_tests.rs`). Rule: never derive a unique name from the clock alone. |
| D-pa-2 | 2026-10-09 | medium | In a pij-fleet clone a bare `git push` pushed only `refs/notes/ai/blocked-by-pij-fleet` (the git-ai notes block) and not the branch, because `.git/config` sets `remote.origin.push` to that ref. The branch silently stayed behind and the placeholder landed on the public remote, so the post-push "`git ls-remote origin refs/notes/*` is empty" check went red. | Root cause: the refspec was added by mistake on 10-08 while creating the placeholder. pij-far-jackal unset `remote.origin.push` and deleted the remote ref; the local placeholder, which is the real block, stays. Still push with an explicit refspec: `git push origin <branch>`. |
| D-pa-3 | 2026-10-09 | high | The smoke fixture builds `target/debug/pij-rs` only when it is missing, so after a daemon change it ran the stale binary. `harness checks` then reported the shim smoke failing for code that was already fixed, and a stale binary can just as easily report green for code that is broken. Same class as "green that lies". | Rebuild before the gate: `cargo build -p pij-cli --bin pij-rs`. `stretch:` the fixture should rebuild whenever sources are newer than the binary, or always run a bounded `cargo build`, which is a no-op when nothing changed. |
| D-pa-4 | 2026-10-09 | medium | EXPLAIN QUERY PLAN tests that run `ANALYZE` on a pool and then explain on that same pool are nondeterministic, because SQLite loads statistics when a connection opens. A pooled connection opened before ANALYZE plans without them. Issue #35 (a `rowid > ?` history scan) appeared on one connection and not another, so probes flickered, and a store-level test passed before the fix. I first misattributed this to a crate feature difference. | Reopen the pool after ANALYZE before explaining (done in both plan tests). Pin hot queries with `INDEXED BY` so the plan is a contract, not a planner preference. |
| D-pa-5 | 2026-10-09 | medium | `harness checks` keeps only the tail of a failing stage's output, so a Rust test failure arrives as "`test failed, to rerun pass -p pij-tmux --test adapter`" with no test name and no assertion. Two `pij-tmux` adapter failures under load could not be attributed, and one real `pij-daemon` failure (an arch guard against raw spine inserts) needed a separate full rerun to identify. | Rerun the named crate directly to read the failure. `stretch:` have the rust stage write the full `cargo test` log to a file and surface its `---- <test> stdout ----` blocks and its failures list in the failure output. |

## Blocking cross-user finding

Atomic mkdir does not specify a private mode and inherits the caller's umask. With umask 002, its lock directory is ordinarily 0775. Another UID in that group can create an owner symlink inside the new directory before the ordinary > redirection at line 254 opens it.

The victim then truncates/overwrites the symlink destination using the victim's permissions. The resulting data is fixed owner metadata, not attacker-selected arbitrary content.

Required conditions: a searchable shared parent, group/world-writable lock permissions and winning the creation race. Attacker configuration control or access to the build cache is unnecessary: an existing private cache under a shared sticky parent is sufficient.

This is a static path/permission finding; no cross-user overwrite was executed. Ordinary umask 022 with protected parents is not exposed to this race. That narrower safe configuration does not satisfy the broader cross-user claim requested in this review.

Minimal repair: atomically create the lock with mode 0700, retain a lock-parent boundary that other users cannot replace, and abort on owner-record write failure. Preserve own-lock cleanup and add a permissive-umask/private-mode regression. Cleanup's lack of directory-identity binding is another reason the protected-parent assumption must be explicit.

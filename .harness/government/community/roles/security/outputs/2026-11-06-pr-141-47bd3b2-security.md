## S001: repository data becomes executable shell syntax

[Step recommendations:437-442](https://github.com/AI-Substrate/pij-fleet/blob/47bd3b2a9cb2fe45d0311a34b04cfc6210d3aa9f/crates/daemon/src/community/picture.rs#L437-L442) and [unowned recommendations:570](https://github.com/AI-Substrate/pij-fleet/blob/47bd3b2a9cb2fe45d0311a34b04cfc6210d3aa9f/crates/daemon/src/community/picture.rs#L570) interpolate repository-authored step labels, needs and blueprint paths into double-quoted --why arguments without shell escaping.

Double quotes permit command substitution and can themselves be terminated. For example, a document-authored step ID s09$(id) needing a missing role produces a reason resembling:

```text
--why "001-x s09$(id) needs role:docs-audit"
```

Running that recommendation executes the substitution. The unowned path repeats the flaw with blueprint where values. Quoting the separate role/project/scope arguments does not protect the reason. The [CLI prints the command strings verbatim:3027-3039](https://github.com/AI-Substrate/pij-fleet/blob/47bd3b2a9cb2fe45d0311a34b04cfc6210d3aa9f/crates/cli/src/main.rs#L3027-L3039).

This is static proof; no exploit was executed. Viewing alone does not execute the payload. Exploitation requires a human or agent to run the printed recommendation, crossing the boundary from repository-authored data into shell syntax. Existing local-machine authority does not make document fields safe shell text.

Required repair: use shell_word on each complete constructed reason instead of wrapping dynamic text in double quotes, in both recommendation paths. Add adversarial recommendation tests covering substitution syntax, double/single quotes, backticks and newlines.

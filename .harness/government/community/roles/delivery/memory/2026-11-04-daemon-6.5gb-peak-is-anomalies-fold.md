# The 6.5 GB daemon peak after the 6ccd4d8 bounce is `pij anomalies` folding the whole spine, not boot

- **date:** 2026-11-04
- **tags:** cost, memory, spine, anomalies, node-show, spine-events, bg.lost, plan-185, plan-187, plan-188, pr-114
- **hook:** Boot reads nothing big. The peak came 27 s after boot from an unscoped `pij anomalies --json`, which decodes all 4.18M spine rows into one Vec. This has happened on every call since the initial release. `node show` and `spine events` do the same.

Answers the prime's msg `839ec87a6f134c8b-0000000000000035` (the perf note `roles/performance/memory/2026-11-04-pr114-deploy-cost.md`). Read-only: code read at `6ccd4d8`, `sqlite3 -readonly` on the live store, the daemon log and session transcripts.

## What happened

- The daemon (pid 97253) started listening at **04:57:04.43Z**. Its log after boot has 3 lines: two "listening" lines and one deduped bg reconciliation refusal for the gone owner `pij-different-smelt`. No startup work logged.
- At **04:57:31.37Z** the PA seat (pij-watchful-badger; corrected by the prime, who checked the session log) ran `pij anomalies --json` unscoped, as skill invariant 12 says to. It returned at **04:57:38.95Z**, after 7.5 s.
- The same session ran `pij node show pij-careful-heron` twice against the **old** daemon at 04:55:48Z and 04:56:21Z. The second took 12 s. The perf note's BEFORE sample (99 MB) is from 04:53–04:54, before those calls. So the old daemon was not immune. It just hadn't been sampled after one.

## The code path

`crates/daemon/src/http/anomalies.rs:67`, in `AnomalyService::list`:

```rust
let events = self.bus.tail(None, Seq(0)).await?;
```

`Spine::tail` → `TAIL_SQL` (`crates/store/src/spine.rs:52`): `SELECT … FROM spine_events WHERE seq > ?1 ORDER BY seq` with `fetch_all`, so there is no LIMIT and no paging. With `since = 0` that is every row. sqlx collects all the rows, then maps them into a `Vec<Event>` (kind, seat and payload are owned Strings). The loop then pushes one `ActivityFact` per event. The whole Vec is also passed to the detectors as `dispositions`, and the status-stale detector scans `activity` once per seat (`crates/core/src/anomalies.rs:306`).

Store at the time of the read (read-only queries):

| | rows | payload bytes |
|---|---:|---:|
| whole spine | 4,175,960 | ~1.55 GB |
| `bg.lost` | 3,585,016 | 1,337,210,998 |
| seat `pij-different-smelt` | 3,591,300 | 1,338,345,248 |
| next-largest seat | 106,117 | 43,840,528 |

One fold reads the whole 2.4 GB file once (the perf note's 2.26 GB disk read). It holds the payloads at least twice, as sqlx rows and then as Events, plus per-row overhead, which puts the peak in the 6.5 GB range. The memory is freed when the request ends: the footprint is 95 MB and vmmap shows the 3.8 GB as "Malloc Small (empty)". RSS drains as macOS reclaims those pages lazily (−350 MB in the measured minute). **It is a per-call spike, not a leak.** Every call reproduces it.

## Other whole-spine reads (same shape, also pre-#114)

| site | verb | what it reads it for |
|---|---|---|
| `http/governance.rs:1497–1503` | `pij spine events` | `tail(None, Seq(0)).last()` only to find the newest seq |
| `http/governance.rs:1510` | `pij spine events --since N` | `tail(None, Seq(N))`, unbounded; `--since 0` is the whole spine, and `--peer` is filtered in Rust after the read, not in SQL |
| `http/governance.rs:1630–1636` | `pij node show` | `tail(None, Seq(0)).last()` only for `cursor` |

`git blame` at 6ccd4d8: all four sites (above plus `anomalies.rs:67`) are `^03ab38e`, the initial public release. **None is new in #114.** #114's startup additions are cheap: migration 0031 is a bare `CREATE TABLE community_pointers`, `Ddocs::from_env` and `CommunityWriter::new` read no store data, and nothing calls `replace_community_pointers` at boot (only the `pointer.rs` tests do). The rest of the boot sequence (`lib.rs:822 boot`) was checked. `reconcile_deliveries` is the plan 185 indexed form, and `park_notice` and event replay page their reads. `bg` uses `latest_matching_message` (LIMIT 1). Raw SQL outside spine.rs (`store/src/decisions.rs`) is scoped by seat or kind. `fleet.rs` runs in the CLI process, not the daemon.

Minor and not whole-spine: `published_or_repair` (`governance.rs:222`) reads `tail(Some(seat), 0)`, i.e. a seat's whole history, on stream, task and prime writes. That is about 100k rows for a busy seat. It is O(history) and worth paging later.

## Proposed fix (the plan 187/188 shape: indexed, bounded, follow the fleet not history)

1. **`node show` and `spine events` cursor:** replace `tail(None, Seq(0)).last()` with `event_bus.newest()`. `Spine::newest` already exists (`events/mod.rs:294`; `SELECT COALESCE(MAX(seq),0)` is a rowid seek). This is a two-line change, and it removes the whole fold from every `node show`.
2. **`spine events --since`:** read with `tail_page(since, limit)` (`TAIL_PAGE_SQL`, keyset on the rowid) under a default and maximum `--limit`, and return the next cursor. When `--peer` is given, seek `SEAT_TAIL_SQL` on `spine_by_seat`. Callers that want everything follow the cursor.
3. **`pij anomalies`:** stop folding the spine. Build the `AnomalyView` from per-seat indexed reads, as `pa_watchdog.rs:1042 stale_cards` already does for the digest:
   - cards: `latest_matching(seat, ["report.now"])`, LIMIT 1;
   - activity: the seat's latest event (one `spine_by_seat` `ORDER BY seq DESC LIMIT 1`; needs a small `Spine::latest(seat)`);
   - `seat.put` for dead-seat facts: LIMIT 1;
   - `report.state` done, `state-verified`, and `anomaly.ack`/`anomaly.clear` dispositions: `all_matching` on `spine_by_seat_kind` (these kinds are small per seat);
   - `delivered_seq` per dispatch: a `(seat, kind='dispatch')` window per recipient;
   - `cursor`: `newest()`.

   Cost then scales as seats × kinds and stays flat as history grows. A seat with 3.59M `bg.lost` rows costs the same as any other.
4. **Proof:** a store test that gives one seat N junk rows and asserts the `pij anomalies` output is identical and the rows read stay bounded. Live, before and after: `pij anomalies --json` wall time (7.5 s today) and `/usr/bin/vmmap -summary <pid>` "Physical footprint (peak)" right after one call on a fresh daemon. No launches are added, so the spawn counters are unchanged.

Separately, deleting the 3.59M junk `bg.lost` rows would shrink every fold by 86%. That is retention, which needs its own ruling (pij#204). The fix above stands without it.
